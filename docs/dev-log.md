The user has no second Google account, so the proof that one account cannot see another's rows is a SQL script for now.
- Installed the dependencies: `@tanstack/react-query` with its two persist packages, `zod`, `expo-network`, `expo-crypto`, and `@react-native-community/datetimepicker`. The last three contain native code, so the development build must be rebuilt before the app imports them. The date picker's config plugin only styles Android dialogs, so `app.config.ts` is unchanged.
- Wrote the migration in `supabase/migrations/`: five tables (`households`, `household_members`, `ingredients`, `batches`, `shopping_items`), row-level security on all of them, no access at all for requests that are not signed in, a trigger that gives each new account a household with ten starter staples, and `apply_changes`, one database function that saves and removes several rows in one transaction. **It is not applied yet:** the user reads it first. `supabase/tests/two_accounts.sql` is the check to run after it.
- One call for every action. The app describes each action as rows to save and ids to remove (`Changes` in `src/data/changes.ts`), applies that to its own copy at once, and will send the same thing to `apply_changes`. Saving a row twice ends in the same state, which is what a queue of offline edits needs, and Undo is the same mechanism run backwards (`undoChanges`).
- Wrote the pure logic test-first, with no screens yet: amounts and units (`1½ lb`, `~2 blocks`, `1 bunch + 3 stalks`), the deduction rule (soonest date first, and "some" takes half and marks the rest as a guess), the date rules (use-soon within 3 days, "Past date, check first", estimates by storage place, no day lost when the clocks change), the Kitchen list's sections, and moving a shopping item into the kitchen. A test compares the app's row checks with the columns in the migration, so the two cannot drift apart.
- Three differences from the draft data model, recorded in `docs/decisions.md`. A purchase keeps the unit it was typed in. A food remembers its usual purchase, which is what "the last amount bought" needs once a food is used up. And `aliases` and `category` wait for the milestones that fill them (6 and 3).
- `npm run check` passes with 186 tests. Not done yet: the migration is not applied, nothing new is on screen, and the slow offline start is not fixed. Next: apply the migration once the user agrees, run the two-account check, then build the offline groundwork.
